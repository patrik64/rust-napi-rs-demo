🦀 napi-rs showcase

One Rust crate.
Two targets.

The same #[napi] functions compiled to a native Node.js addon for the server and to WebAssembly for the browser — demonstrated live in a SvelteKit app.

JavaScript is great — until it isn't

  • CPU-bound work — image processing, parsing, hashing, number crunching — fights the JIT and blocks the event loop.
  • The classic escape hatches each hurt: C++ addons (node-gyp, ABI pain) or hand-rolled WASM (its own toolchain, no Node integration).
  • And they are two different codebases if you need both server and browser.

napi-rs: one macro, the whole story

  • Annotate plain Rust with #[napi] → it becomes a JavaScript export via Node-API.
  • TypeScript definitions generated for free — the same index.d.ts for both targets.
  • v3's headline: napi build --target wasm32-wasip1-threads compiles the unchanged crate to WASM — threads, tokio and all.
  • Battle-tested: Rspack, Rolldown, oxc, Prisma, Tailwind v4's Oxide…

The whole trick

use napi_derive::napi;

#[napi]
pub fn greet(name: String) -> String {
    format!("Hello {name}, this string was built in Rust 🦀")
}

#[napi]
pub fn fibonacci(n: u32) -> u32 { /* … */ }

#[napi]
pub async fn fibonacci_async(n: u32) -> Result<u32> { /* … */ }

napi build --platform → demo.darwin-arm64.node  ·  napi build --target wasm32-wasip1-threads → demo.wasm32-wasi.wasm

What crosses the boundary

  • Strings & numbers — greet(name)
  • Uint8Array ↔ &[u8] — zero-copy in
  • #[napi(object)] structs → plain JS objects, fields auto-camelCased
  • async fn → Promise (tokio on a worker)
  • Result<T> → JS exceptions
  • The whole crates.io ecosystem: image, pulldown-cmark, …

Gotcha #1

Cross-origin isolation — on every response

  • Threaded WASM needs SharedArrayBuffer → the page must be cross-origin isolated:
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
  • A worker script served without its own COEP header is silently refused — sync WASM keeps working, only threads/async die.
  • Dev: Vite server.headers covers everything. Prod: wrap the adapter-node handler — SvelteKit's asset middleware bypasses hooks.server.ts.
Gotcha #2

Pin the toolchain generation

The cargo and npm halves must come from the same emnapi generation (v1 stable vs v2 alpha, July 2026):

PackagePinnedBecause
napi-build (cargo)=2.3.22.4 links emnapi-v2-only symbols
@napi-rs/cli3.7.33.7.4+ emit v2-alpha loaders
emnapi · @emnapi/core · @emnapi/runtime1.11.x, all equalCLI enforces equality
@napi-rs/wasm-runtime1.1.61.2.0 peer-depends on core v2-alpha

Commit your lockfiles. Symptoms of mixing: linker errors, "emnapi version mismatch", missing ./plugins subpath.

Which target, when?

Native addon

  • Fastest — full CPU, real threads
  • OS access (fs, sockets, GPUs)
  • Per-platform binaries to ship

WASM (same crate!)

  • Runs in browsers, StackBlitz, edge
  • One artifact, no platform matrix
  • ~1.5–5× slower, isolation headers

With napi-rs you don't choose — publish the native addon with a WASM fallback, and the generated loader picks at runtime.
