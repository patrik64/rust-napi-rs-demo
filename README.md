# napi-rs showcase — one Rust crate, two targets

Talk demo: a SvelteKit app where the **same Rust crate** (`native/src/lib.rs`)
runs as

- a **native Node.js addon** (`demo.darwin-arm64.node`) inside the SvelteKit
  server, and
- a **WebAssembly module** (`demo.wasm32-wasi.wasm`, threaded WASI build)
  inside the browser —

both generated by [napi-rs](https://napi.rs) v3 from identical `#[napi]`
functions, with shared TypeScript definitions.

```
 rust-napi-rs-demo/
├── native/              # the Rust crate
│   ├── src/lib.rs       # ← the single source of truth (all demo functions)
│   ├── Cargo.toml       # napi 3.11 + image + pulldown-cmark
│   ├── .cargo/config.toml  # --cfg tokio_unstable for the wasm target
│   └── package.json     # @napi-rs/cli config; exports "." (native) and "./wasm"
└── app/                 # SvelteKit (Svelte 5, Vite 8, adapter-node)
    ├── src/routes/api/  # server endpoints calling the native addon
    ├── src/lib/wasm.ts  # lazy browser-side loader for the WASM build
    └── server.mjs       # production entry (adds COOP/COEP to every response)
```

## Prerequisites

- Node ≥ 20, pnpm
- Rust toolchain + the WASI threads target:
  `rustup target add wasm32-wasip1-threads`

## Quick start

```bash
pnpm install
pnpm build:native   # cargo → native/demo.darwin-arm64.node + index.js/.d.ts
pnpm build:wasm     # cargo → demo.wasm32-wasi.wasm + browser/node loaders
pnpm dev            # http://localhost:5173
```

Production: `pnpm build && pnpm preview` (serves via `app/server.mjs`).

## The demo pages (suggested talk flow)

1. **Overview** — `greet()` runs twice: once natively during SSR, once as WASM
   after hydration. Then the event-loop demo: blocking `fibonacci(40)` freezes
   a rAF-driven dot; `await fibonacciAsync(40)` (Rust `async fn` → JS Promise,
   tokio on a worker thread) keeps it moving.
2. **Benchmark** — the same naive fibonacci in 4 engines: browser JS, browser
   WASM, server JS, server native. Typical result on an M-series MacBook at
   n = 35: JS ~60 ms, WASM ~32 ms, native ~25 ms.
3. **Image** — the `image` crate (grayscale/invert/pixelate/blur) fed a
   `Uint8Array`, switchable between browser-WASM and server-native.
4. **Text** — `pulldown-cmark` markdown rendering plus a `#[napi(object)]`
   struct returned as a plain JS object, re-run on every keystroke.

Feature checklist covered by `lib.rs`: strings, numbers, `Uint8Array` buffers,
`#[napi(object)]` structs (camelCase conversion), `async fn` → Promise,
`Result` → JS exceptions, crates.io reuse.

## How the two builds are wired

- **Server**: endpoints in `app/src/routes/api/*` simply
  `import { fibonacci } from '@demo/rust'` — the generated `index.js` picks the
  `.node` binary. Vite treats the package as `ssr.external`.
- **Browser**: `import('@demo/rust/wasm')` resolves to the generated
  `demo.wasi-browser.js`, which fetches the `.wasm`, instantiates it with a
  shared `WebAssembly.Memory`, and spawns `wasi-worker-browser.mjs` workers
  for threads/async tasks.

### Cross-origin isolation (the #1 deployment gotcha)

The threaded WASM build needs `SharedArrayBuffer`, which requires:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

- Dev: set via `server.headers` in `vite.config.ts` (covers every response).
- Prod: `app/server.mjs` wraps the adapter-node handler. **The headers must
  also be on static assets** — a worker script served without its own COEP
  header is refused in an isolated page, which silently breaks only the
  async/threaded path (`hooks.server.ts` alone is not enough; SvelteKit's
  asset middleware bypasses it).

Also required in a pnpm monorepo: `server.fs.allow` must include the workspace
root so Vite may serve the loader files from `../native`.

## Version pinning  

The npm and cargo halves of the WASM toolchain must come from the same
generation. As of July 2026 the stable, mutually compatible set used here:

| Package | Version | Why |
|---|---|---|
| `napi-build` (cargo) | `=2.3.2` | 2.4.0 links the emnapi **v2 alpha** symbol scheme (`emnapi_create_env`) |
| `napi` (cargo) | 3.11.x | pairs with napi-build 2.3 |
| `@napi-rs/cli` | `3.7.3` | 3.7.4/3.8.0 generate loaders importing `@emnapi/core/plugins` (v2-alpha-only) |
| `emnapi` / `@emnapi/core` / `@emnapi/runtime` | 1.11.x (all equal) | CLI enforces the three being identical |
| `@napi-rs/wasm-runtime` | `1.1.6` | 1.2.0 peer-depends on `@emnapi/core@^2.0.0-alpha` |

Symptoms of mixing generations: `emnapi version mismatch`, linker errors
`symbol exported via --export not found: emnapi_create_env`, or runtime
`Package subpath './plugins' is not defined`. Once emnapi v2 is stable, moving
*everything* to the new line should undo all pins.

`native/.cargo/config.toml` additionally sets `--cfg tokio_unstable` for
`wasm32-wasip1-threads` — without it napi's async support rejects at runtime
with "Built-in Tokio async tasks require a threaded WASI target".

## Regenerating from scratch

All build artifacts (`*.node`, `*.wasm`, `index.js`, `index.d.ts`, loaders,
workers) are gitignored and reproducible with the two build commands above.
